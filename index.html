01 / THE USE CASE

A handoff should move
the work forward.

Company-formation services have a long customer journey: enquiries, consultations, quotes, payment, documents, filing, and delivery. When each step lives in a separate tool, teams lose context.

This project brings that journey into a role-aware workspace. Sales works the pipeline, accounts tracks the ledger, operations manages the filing stages, and clients see progress through a portal.

The public demo narrows this down to one understandable story: qualify a lead, prepare a proposal, simulate a payment, and follow the delivery handoff.

02 / ENGINEERING DECISIONS

The rules behind
the interface.

A

A shared intake path

Normalize contact identifiers before matching an existing open enquiry. Multiple channels should not create competing copies of the same opportunity.

Channel → normalize → deduplicate → route
B

Guard the transitions

Require the right facts before moving a deal forward. In the demo, a follow-up requires a date; a proposal requires a quote; a won deal requires a recorded demo payment.

Validate facts → permit transition → log event
C

Reconcile from the ledger

The application reads received payments from ledger rows when closing a deal. This avoids treating a previously received payment as new money at close.

Received = sum of received ledger entries
D

Authorize on the server

The original application separates staff from portal sessions and checks roles before privileged actions. Database policies add another layer. The public demo only illustrates a workflow; it does not implement authentication.

Session → staff identity → permission → database policy
